# Billing

> **Where the 77 € comes from.** One map view in the MML example planned
> **193 088 byte ranges**. Issued as written, on S3 at list price, that is
> **$0.0772 per view** — and **$77.24 per thousand views**. Coalesced, the same
> view is **9 requests, $0.0000036** — **$0.0036 per thousand**. A ratio of
> **21 454×**, decided by one parameter.
>
> That is the whole reason this document exists, and the reason the library
> refuses a query instead of merely logging it.

All figures below come from `tools/cost-report.js`, which builds a 200 000-document
artifact and measures every query shape. Re-run it any time:

```
node tools/cost-report.js --docs 200000 --host s3 --md
```

---

## 1. What you are actually billed for

An L0 artifact is one immutable object on static storage. There is no server, no
node, no provisioned cluster. So the bill has exactly three lines:

| line | S3 (same region) | S3 → internet | CloudFront | GitHub Pages |
|---|---|---|---|---|
| **requests** | $0.40 / million GET | $0.40 / million | $0.75 / 10 M | — |
| **bytes out** | $0 | $0.09 / GB | $0.085 / GB | — (100 GB/mo quota) |
| **storage** | $0.023 / GB·month | same | — | 1 GB site limit |

Two things follow immediately, and they are the two things people get wrong.

**Requests, not round trips, are what you pay for.** These are different
quantities and the distinction is the entire subject of this document. A wave of
50 000 parallel range GETs is *one round trip* — it is fast, it feels free, the
latency numbers look wonderful — and it is *50 000 billable requests*. Optimising
for latency and optimising for money are not the same exercise, and an index that
plans its I/O in parallel waves will happily make you very fast and very poor.

**In-region reads are request-priced, not byte-priced.** Running the reader in a
Lambda in the bucket's region makes bytes free, which inverts the usual
intuition: fetching 3 MB in 2 requests is *cheaper* than fetching 300 kB in 40.
That is why the coalescing policy in §3 optimises request count under a byte
ceiling rather than minimising bytes.

Read that table as three groups.

**Cheap and flat (almost everything).** A `term`, a `range` on the clustering
key, `exists`, a paged fetch of documents: 2 rounds, 2 requests, well under a
microdollar. These touch one or two bitmaps and one or two stored blocks. The
cost does not grow with corpus size — it grows with how many *distinct values*
the predicate names.

**The clustering key is the cheapest predicate there is.** `range on the
clustering key` returns 5 840 hits for 0.06 MB. The same selectivity on a
non-clustering numeric costs 1.18 MB — 20× the bytes — because a predicate
outside the clustering key selects *rows*, not *bytes*. This is the central
finding of the whole project and it is a billing fact as much as a latency one.

**One shape is dangerous, and it is always the same shape.** `terms agg over
50 000 distinct values` plans 50 000 ranges. One bitmap per value is the correct
plan — it is why the aggregation is exact and costs one round trip — but as
50 000 separate GETs it is **$0.02 per query, $20 per thousand**. Everything
expensive in this index has this form: *one byte range per distinct value of a
high-cardinality field.*

## 3. Why coalescing is a precondition, not an optimisation

Merging nearby ranges into one GET turns 50 000 requests into 1. The gaps get
fetched too, so the trade is bytes for requests.

idx_research §13.4 derived the merge rule as *gap < latency × bandwidth* (~3 MB
on S3). **That derivation is wrong for a parallel wave.** It assumed the
alternative to merging was a second round trip. In a wave the alternative is one
more independent range at essentially zero added latency — so merging there buys
nothing and costs bytes. Measured: the 20-value `terms` query plans 21 ranges;
a naive 64 kB merge makes it 2 requests and **0.77 MB instead of 0.10 MB, a 7.8×
over-fetch, for no round trip saved**.

The corrected rule, implemented in `src/transport/coalesce.js`:

1. Merge touching or overlapping ranges. Always — it is free.
2. If the count is already under the concurrency budget, **stop**. Those requests
   are concurrent; only bytes remain, and merging only adds bytes.
3. Otherwise widen the gap until the count fits the budget. This is what collapses
   50 000 → 1 and 193 088 → 9.
4. Stop widening if it would pull more than `maxFetchBytes` (64 MB default). Past
   that the query is genuinely expensive, and the right answer is to refuse it —
   not to quietly buy the whole artifact.

The over-fetch column in the table above is `1.00×` on every row. That is this
policy working: the expensive shapes still collapse, and the cheap ones are left
alone.

## 4. The guard

A budget is checked **before each wave is issued**, at the one chokepoint where
the complete request list is known and no byte has been fetched yet
(`Reader._wave`). It bills the *coalesced* plan, because that is what will
actually be charged.

```js
import { Reader } from 'serverless-index';
import { HttpTransport } from 'serverless-index/browser';

const reader = await new Reader(new HttpTransport(url), {
  budget: { requests: 2048, bytes: 256e6, rounds: 8, usd: 0.001, host: 's3' },
}).open();
```

Any limit can be set; all are optional. Exceeding one throws `BudgetExceeded`
before I/O, with the diagnosis:

```
query refused: requests 193,088 > limit 1,000
  this wave: 193,088 requests, 197.7 MB, $0.077235 on S3, same region
  the transport does not coalesce; with a 64 kB gap this wave would likely
  collapse to a handful of requests. Pass {coalesceGap: 65536}.
  ranges by field:
    bm:kaupallinenNimi           193,088
  [bm:kaupallinenNimi] dominates. A terms aggregation over a high-cardinality
  field asks for one range per value; reduce its size, or move the selector
  into the clustering key so the rows are contiguous.
```

The message names the field because the range keys carry it (`bm:<field>:<value>`,
`col:<field>:values`, `tri:<field>:<gram>`). The field name is the actionable
fact: nobody can act on "too many requests."

`mode: 'warn'` reports through `onReport` and continues, for measuring an existing
workload before turning enforcement on.

### Suggested limits

| deployment | limits | why |
|---|---|---|
| Lambda, in-region | `{requests: 2048, rounds: 8, usd: 0.001}` | bytes are free; requests and dependent rounds are the cost |
| Browser, S3/CloudFront | `{requests: 512, bytes: 64e6}` | bytes are billed *and* are the user's wait |
| Browser, GitHub Pages | `{requests: 4096, bytes: 512e6}` | no request price; the 100 GB/month quota is the limit |
| CI / test | `{requests: 64, rounds: 4, mode: 'throw'}` | catches a regression in query shape at review time |

The Lambda adapter sets a default budget and returns a refusal as **HTTP 400**
with the diagnosis in the body — the client's query is at fault and is
fixable — rather than a 500 and a surprise invoice. It also returns
`x-l0-requests`, `x-l0-bytes`, `x-l0-rounds` and `x-l0-usd` on every response,
so the cost is visible in ordinary access logs.

## 5. GitHub Pages

Pages charges nothing per request and nothing per byte, but has a **100 GB/month**
soft bandwidth quota, a **1 GB** site limit and a **100 MiB** per-file block
(hence `ChunkedHttpTransport` and `tools/split-artifact.js`). Range requests are
supported — verified, `206` with a correct `content-range`.

The quota is the budget. `estimate(..., 'pages')` reports it directly as
`viewsPerMonth`: a 114 MB view is ~877 views a month. Caching changes this
completely — the catalog and the hot sections are immutable and will be served
from the browser cache or a CDN edge, so a returning visitor costs nearly
nothing. An artifact's sections can never be stale, which is exactly why
`Cache-Control: immutable` is correct here and dangerous almost everywhere else.

## 6. Lambda itself

Not in the table because it is not the interesting part, but for completeness: a
128 MB Lambda at 400 ms costs about **$0.00000083** per invocation — a fifth of
one coalesced query's S3 GETs. Cold start on a small Lambda is on the order of
100–200 ms locally; against an S3-backed artifact, 400–600 ms end to end is the
realistic figure. The reader is cached per container, so a warm invocation skips
the catalog fetch entirely and answers a repeat facet query **with no network at
all** — a cached section of an immutable artifact can never be wrong.

Segment count costs memory and bytes, not latency.

## 7. Rules of thumb

- Price **requests**, not round trips. They diverge by four orders of magnitude.
- **One range per distinct value** is the expensive shape. Find it by looking for
  a high-cardinality field in a `terms` aggregation, a `prefix`, or a `wildcard`.
- Put the selector you filter on most into the **clustering key**. Nothing else
  reduces bytes; everything else only reduces rows.
- Never merge ranges that already fit one parallel wave.
- Set a budget in production. The cost is knowable before the first byte moves,
  so there is no excuse for finding out from the invoice.
